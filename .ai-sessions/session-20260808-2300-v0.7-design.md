# Session Summary: v0.7 Design (Permanent Spec, Invariants, Rule Vendoring)

**Date**: 2026-08-08
**Duration**: ~1 hour
**Conversation Turns**: ~9 user prompts
**Estimated Cost**: moderate (design discussion, one file written, one commit ritual)
**Model**: Opus 4.8

## Key Actions

- Compared BPE against the Ng/Everitt spec-driven playbook (DeepLearning.AI x JetBrains, April 2026); mapped all ten of their rules onto BPE and identified two real gaps (first-class constraints, first-class out-of-scope) plus one latent role confusion in spec.md.
- Worked through whether BPE should adopt a write-once constitution; landed on a permanent spec.md using pace layering (mission/invariants slow, requirements medium, plan/todo fast) rather than a separate constitution file, since BPE is one-spec-per-repo.
- Resolved five design forks via AskUserQuestion: brainstorm merge mode for phase N+1, both new passes stay in brainstorm, mixed structured/prose constraints, retrofit gains a resync role for drift, and invariants materialized at project level.
- Solved the writing-style portability problem: two channels (spec Invariants for the BPE loop, committed `.claude/rules/` for every agent including collaborators), a vendoring model (skills as source, repo files as frozen output), and three buckets (always vendor craft, conditionally vendor doc-hygiene, never vendor personal voice).
- Wrote `v0.7-plan.md` at the repo root as the durable design record, with the decisions, rationale, per-file change set, backwards-compat stance, deferred items, and a resume entry point.
- Created the `v0.7` branch and ran the commit ritual to land the plan.

## Efficiency Insights

**What went well:**
- Reading the core skills (brainstorm, plan, execute-plan, goal) before comparing meant the comparison was grounded in the actual artifacts, not the README.
- AskUserQuestion with per-option previews made the five design forks fast to decide.

**What could improve:**
- Offered a separate three-file constitution split in an early turn before checking that BPE is one-spec-per-repo; the single-file answer was reachable sooner.

**Course corrections:**
- Retracted the alarm that spec.md "is really a phase doc" once the user clarified the direction is a permanent spec and the phase-shaped specs are legacy.

## Process Improvements

- When a design decision hinges on cardinality (one spec per repo vs many), establish that first; it determines whether a separate file is justified.
